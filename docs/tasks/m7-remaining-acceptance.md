## 建议验收顺序与依赖

1. 先V01逐预期证据核对，区分现有软件已证明、需要补测试和需要真人/环境；V02可作为独立短切片修补已知Minor。避免无变化地反复执行已通过的完整门禁。
2. 当前设备优先V03/V04，补键盘/VoiceOver/视觉；同时准备V05/V06隔离Mac测试账号，开展真实原生链路。每次只登记实际完成的Mac格子。
3. 尽早准备V08验收服务器/HTTPS/SMTP、V09 Windows/Linux环境和V12签名条件。V08就绪后开始V11.2实际介质留存观察，以免最后才开始等待真实周期。
4. V08与各OS环境就绪后完成V07目标浏览器/网络矩阵、V09-W/L原生验证；V12签名验证在相应包和测试系统就绪后进行，不发布。
5. 有确定旧候选和数据后做V10；在对应库/key/恢复设备就绪后完成V11.1/.2/.3。不要将同构建替换当历史版本兼容，也不引入在线多实例key轮换。
6. 最后V13在实际候选上走A60正常/异常旅程并逐项签收A01–A60，整理交付和已知限制。若修补产品/核心流程，按规则重新冻结并运行适用完整verify；文档核对或环境准备不机械重跑全部测试。

每完成2–3个小批次检查：候选/设备版本和证据对应、未碰已有个人状态、夹具按已证明的具体ID清理、原待验项未被顺带勾选。只有原叶子全部完成标准满足才勾T；通过某一OS/版本或纯软件切片不关闭完整矩阵。允许A项逐个据实签收，不批量补签；历次已授权补证执行不改变现有正式待验状态。

当前建议下一次范围：**选择V01剩余部分证据/联合旅程做软件补证，另由验收人员开展V03/V04；Mac原生测试账号准备好后再V05/V06。** 外部环境准备可并行；V03之后和产品补证需后续授权，正式部署与发布均不是这份计划的执行授权。
