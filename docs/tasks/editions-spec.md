# 发行形态规格 · 单机版与云服务版

日期：2026-10-28。状态：**已授权（E00–E07 于 2026-10-28 通过）**，实施范围为 E01–E09。决策依据 [012](../decisions/012-edition-split-and-local-startup.md)；任务切片见 [发行形态任务](./editions-todo.md)。本文件不改变 A01–A60 的既有权重，只界定各断言的适用发行形态。

## 问题

当前只有一种运行方式：手动备齐 17 个 `MCP_STUDIO_*` 环境变量后启动 Go 平台，`npm run dev` 仅起前端，部署依赖 `apps/cloud/deploy/` 下的 Compose 三服务。缺少"单人本地直接可用"的形态，也缺少两种形态之间明确的边界与默认值。

## 目标

同一份业务代码产出两种发行形态：

- **单机版**：一个进程启动，内嵌前端静态资源与 PostgreSQL，首启初始化到用户数据目录，自动打开浏览器；免登录，无团队与邀请概念；凭据进系统凭据库。
- **云服务版**：现有 Compose 三服务（db、platform、tls），Caddy 终止 HTTPS，浏览器访问；完整账号、团队、项目与权限语义。
- **开发态**：一条命令起 PostgreSQL、平台与前端；Agent 单独启动。

## 非目标

- 不做多租户共用部署（一个部署 = 一个团队）。
- 不做 K8s / 托管 PaaS 适配。
- 不引入 Electron / Tauri 桌面壳。
- 不改变 Agent 的配对方式与终端确认环节。
- 不为单机版实现第二套数据层（不换 SQLite）。
- 不在本阶段处理签名、公证与自动更新分发链路，仅登记为待验。

## 行为约定

| 维度 | 单机版 | 云服务版 |
| --- | --- | --- |
| 进程数 | 1（自带 PG 子进程或内嵌实例） | 3 服务 + 前端静态资源 |
| 数据库 | 同一套迁移，用户数据目录内 PG 数据目录 | 独立持久卷的 PostgreSQL |
| 首启 | `initdb` + 建本地主体 + 建个人项目 | 由 `_FILE` 提供初始化凭证建管理员 |
| 登录 | 无登录界面；本地主体恒为当前主体 | 会话登录 |
| 角色校验 | 跳过角色与成员资格校验 | 完整校验，模拟角色不是授权来源 |
| 数据可见范围 | **保留按项目归属过滤** | 完整校验 |
| 传输 | 回环，无 TLS | Caddy 终止 TLS |
| 凭据 | 系统凭据库（Keychain / libsecret / DPAPI） | 平台加密列 + 服务端备份密钥 |
| 数据目录 | macOS `~/Library/Application Support/MCP Studio/`；Linux `~/.local/share/mcp-studio/`；Windows `%LOCALAPPDATA%\MCPStudio\` | 容器卷 |

## 不变量

- 业务领域代码、合同、迁移、前端只有一份；两个发行目录只承载入口、默认配置与分发资产。
- 原始请求响应与会话凭据不进浏览器持久存储；单机版不因免登录而放宽该约束。
- 秘密不写进 URL、日志、Toast、默认复制或仓库。
- 执行、上传、保存修订分离；每 Run 一个上传责任端。
- 单机版的本地主体是库中真实账号，不是模拟角色；其存在不改变云版的授权判据。

## 验收标准

1. 单机版在一次安装后，双击或单条命令即可启动并打开可用工作台，无需预装 Go、Node 或 PostgreSQL。
2. 单机版首次启动完成 `initdb`、本地主体与个人项目初始化，二次启动不重复初始化。
3. 单机版在存在第二个项目时，查询仍受项目归属过滤，不返回跨项目内容。
4. 云服务版在 Compose 下以浏览器 HTTPS 访问，秘密仅经 `_FILE` 挂载，平台与 db 无 host port。
5. 两版由同一份 `internal/` 与 `apps/web` 构建；改动业务逻辑后两侧同时生效，无需重复修改。
6. `npm run dev` 单条命令得到可用的开发环境；Agent 通过独立命令启动并保留终端确认。
7. `npm run verify` 覆盖两版构建与单机版启动冒烟；未执行前不得报告任一形态通过。

## 依赖与风险

- **两套授权语义是长期成本**：云版越权排查需先排除单机分支；若将来单机版补回登录，应删除编译分支而非叠加。
- **schema 不分叉**：单机版库中仍存在账号、团队、项目表，备份与恢复不得假设这些表为空。
- **内嵌 PG**：每架构约 +50MB；PG 大版本升级需处理既有数据目录，属新增运维面。
- **待验范围扩大**：A41、A42 与新增的签名/公证均依赖本机 OS 与真实介质，缺环境时只能停留在未签名内部试用。
- **规则修订**：`AGENTS.md` 权限边界需按 012 的建议文本改写，否则规则与实际行为冲突。

## 新增待验项

以下三项因缺环境只能登记为待验，与 [012](../decisions/012-edition-split-and-local-startup.md) 的风险节一致；未执行前不得报告对应形态通过。

| 项 | 内容 | 为什么待验 | 解除条件 |
| --- | --- | --- | --- |
| 内嵌 PG 首启 | 随包 PG 二进制的校验、干净数据目录 `initdb`、二次启动不重复初始化、大版本不兼容时明确拒绝 | 需要各平台真实干净目录与安装介质；当前只有本机 macOS 容器内 PG | E05／E06 完成后在 macOS、Linux、Windows 各自干净目录首启并留证 |
| 单机版凭据库 | Keychain／libsecret／DPAPI 的实际读写、锁定与不可用时的降级 | 需要真实 OS 凭据库与真人确认；现有 Agent 自动证据注入的是测试主密钥 | E05／E06 完成后在三个 OS 实机验证，不注入测试主密钥 |
| 签名与公证 | macOS 签名／公证、Windows 签名、Linux 包完整性 | 无签名身份、开发者账户与目标证书 | 取得身份与证书后签名并复核；本阶段不实施分发链路 |

A41、A42 的适用形态据此扩大：单机版同样依赖系统凭据库与真实 OS 确认。
